A release should be boring. Change the version, push to `main`, and let the pipeline do the rest: create a tag, write the GitHub Release, attach clean notes, and publish the container image.

That is the goal of this workflow. It uses one small file, `VERSION`, as the release switch. When `VERSION` changes on `main`, GitHub Actions reads the value, creates a matching tag like `v1.0.1`, builds release notes from the commits since the previous tag, publishes a GitHub Release, and pushes a Docker image to GitHub Container Registry.

This post covers both sides: how to write the workflow, and how to use it without thinking about the details every time.

## The Release Model

The setup is intentionally simple:

| Input | Purpose |
|---|---|
| `VERSION` | The source of truth for the release number |
| Commit messages | The source of truth for release notes |
| Git tags | The boundary between releases |
| GitHub Release | The public changelog for users |
| GHCR image tags | The deployable artifact |

The workflow does not guess the next version. It waits for a human to change `VERSION`.

That makes the release moment explicit:

```txt
1.0.0
```

becomes:

```txt
1.0.1
```

Once that change is pushed to `main`, the release pipeline starts.

## Why Use a VERSION File

There are many ways to trigger releases: tags, merged pull requests, npm package versions, semantic-release, or manual dispatch.

For a small site or application, a plain `VERSION` file is often easier to maintain. It has three advantages:

1. It is visible in the repository.
2. It is easy to review in a pull request.
3. It avoids accidental releases from ordinary code pushes.

The workflow can be configured to run only when `VERSION` changes:

```yaml
on:
  push:
    branches: [main]
    paths:
      - VERSION
  workflow_dispatch:
```

The `paths` filter matters. A normal documentation edit or CSS fix will not publish a new release unless the version file is also changed.

## Workflow Permissions

The release job needs permission to create tags, create GitHub Releases, and push a package to GHCR.

```yaml
permissions:
  contents: write
  packages: write
```

`contents: write` allows the workflow to push the tag and create the GitHub Release. `packages: write` allows it to push the Docker image to GitHub Container Registry.

Without these permissions, the workflow may build successfully but fail at the publishing step.

## Checkout with Full History

Release notes are generated by comparing the current commit with the previous tag. For that, the workflow needs tags and enough git history.

```yaml
- name: Checkout
  uses: actions/checkout@v4
  with:
    fetch-depth: 0
```

The default checkout is shallow. That is fine for many CI jobs, but not for changelog generation. `fetch-depth: 0` gives the job the history it needs to run commands like:

```bash
git describe --tags --abbrev=0
git log v1.0.0..HEAD --oneline --no-merges
```

## Reading VERSION

The release version is read from the `VERSION` file and written to GitHub Actions outputs.

```yaml
- name: Read VERSION
  id: ver
  run: |
    VERSION=$(cat VERSION | tr -d '[:space:]')
    echo "version=${VERSION}" >> "$GITHUB_OUTPUT"
    echo "tag=v${VERSION}" >> "$GITHUB_OUTPUT"
```

If `VERSION` contains:

```txt
1.0.1
```

then the workflow outputs:

```text
version=1.0.1
tag=v1.0.1
```

Later steps can use those values:

```yaml
${{ steps.ver.outputs.version }}
${{ steps.ver.outputs.tag }}
```

## Avoiding Duplicate Releases

A release should not be created twice for the same version. Before doing any publishing work, the workflow checks whether the tag already exists on the remote.

```yaml
- name: Check tag exists
  id: tag_check
  run: |
    if git ls-remote --tags origin \
         "refs/tags/${{ steps.ver.outputs.tag }}" | grep -q .; then
      echo "exists=true" >> "$GITHUB_OUTPUT"
    else
      echo "exists=false" >> "$GITHUB_OUTPUT"
    fi
```

Every publishing step can then use the same guard:

```yaml
if: steps.tag_check.outputs.exists == 'false'
```

If `v1.0.1` already exists, the workflow exits quietly instead of overwriting the release.

## Generating Release Notes from Commits

The release notes come from commit subjects since the last tag.

```bash
LAST_TAG=$(git describe --tags --abbrev=0 2>/dev/null || echo "")

if [ -n "$LAST_TAG" ]; then
  COMMITS=$(git log "${LAST_TAG}..HEAD" --oneline --no-merges)
else
  COMMITS=$(git log --oneline --no-merges)
fi
```

The first release has no previous tag, so the workflow uses all commits. Later releases use only the commits after the last tag.

For example:

```text
a2c9b56 fix(mermaid): fix node text clipping in flowchart diagrams
dad844c feat(about): rewrite About page and homepage description
35fc70e feat(posts): add Dependabot and Conventional Commits guides
9d2a111 docs(posts): update the release guide
7b64053 chore: add wrangler.toml
```

The workflow reads each line, splits the hash from the message, and classifies it.

```bash
HASH=$(echo "$line" | cut -d' ' -f1)
MSG=$(echo "$line" | cut -d' ' -f2-)
```

Messages beginning with `fix:` or `fix(scope):` go to `Bug Fixes`:

```bash
if echo "$MSG" | grep -qiE "^fix(\([^)]*\))?:"; then
  CLEAN=$(echo "$MSG" | sed -E \
    's/^fix\(([^)]+)\): /\1: /i; s/^fix: //i')
  FIX_LINES="${FIX_LINES}- ${CLEAN} (${HASH})\n"
fi
```

Messages beginning with `feat:` or `feat(scope):` go to `Features`:

```bash
elif echo "$MSG" | grep -qiE "^feat(\([^)]*\))?:"; then
  CLEAN=$(echo "$MSG" | sed -E \
    's/^feat\(([^)]+)\): /\1: /i; s/^feat: //i')
  FEAT_LINES="${FEAT_LINES}- ${CLEAN} (${HASH})\n"
fi
```

Everything else is omitted from the public Release Notes. That includes `docs`, `chore`, `ci`, and one-off messages like `update`.

## What Commit Messages Should Look Like

This workflow expects a small Conventional Commits subset.

Use `fix` for bug fixes:

```bash
git commit -m "fix(mermaid): fix node text clipping in flowchart diagrams"
```

That becomes:

```md
## Bug Fixes

- mermaid: fix node text clipping in flowchart diagrams (a2c9b56)
```

Use `feat` for new features:

```bash
git commit -m "feat(posts): add Dependabot guide"
```

That becomes:

```md
## Features

- posts: add Dependabot guide (35fc70e)
```

Use `docs` for articles and documentation:

```bash
git commit -m "docs(posts): update GitHub Actions release guide"
```

That commit stays in git history, but it does not appear in the GitHub Release.

Use `chore` or `ci` for maintenance work:

```bash
git commit -m "chore: release 1.0.1"
git commit -m "ci: update release workflow"
```

Those commits are also omitted. The release page is reserved for user-facing fixes and features.

If a release contains no `fix` or `feat` commits, the body says:

```md
No user-facing changes.
```

The important part is consistency. The workflow is simple because the commit messages carry enough structure.

## Creating the Git Tag

After the notes are generated, the workflow creates an annotated tag.

```yaml
- name: Create git tag
  if: steps.tag_check.outputs.exists == 'false'
  run: |
    git config user.name "github-actions[bot]"
    git config user.email "github-actions[bot]@users.noreply.github.com"
    git tag -a "${{ steps.ver.outputs.tag }}" \
            -m "Release ${{ steps.ver.outputs.tag }}"
    git push origin "${{ steps.ver.outputs.tag }}"
```

Annotated tags are useful because they carry a message and are treated as first-class release markers.

For version `1.0.1`, the tag is:

```text
v1.0.1
```

## Publishing the GitHub Release

The workflow uses `softprops/action-gh-release` to publish the release.

```yaml
- name: Create GitHub Release
  if: steps.tag_check.outputs.exists == 'false'
  uses: softprops/action-gh-release@v2
  with:
    tag_name: ${{ steps.ver.outputs.tag }}
    name: ${{ steps.ver.outputs.tag }}
    body_path: ${{ steps.notes.outputs.notes_path }}
    draft: false
    prerelease: false
```

The important field is `body_path`. The workflow writes the release notes to a temporary file, then passes that file to the release action.

This keeps the release body readable and avoids escaping multiline Markdown inside YAML.

## Publishing the Docker Image

The same release can publish a Docker image.

```yaml
- name: Set up Docker Buildx
  if: steps.tag_check.outputs.exists == 'false'
  uses: docker/setup-buildx-action@v3

- name: Log in to GHCR
  if: steps.tag_check.outputs.exists == 'false'
  uses: docker/login-action@v3
  with:
    registry: ghcr.io
    username: ${{ github.actor }}
    password: ${{ secrets.GITHUB_TOKEN }}
```

Then `docker/metadata-action` creates the tags:

```yaml
tags: |
  type=semver,pattern={{version}},value=${{ steps.ver.outputs.version }}
  type=semver,pattern={{major}}.{{minor}},value=${{ steps.ver.outputs.version }}
  type=raw,value=latest
```

For `1.0.1`, that produces:

```text
ghcr.io/owner/repo:1.0.1
ghcr.io/owner/repo:1.0
ghcr.io/owner/repo:latest
```

Finally the image is built and pushed:

```yaml
- name: Build & push image
  if: steps.tag_check.outputs.exists == 'false'
  uses: docker/build-push-action@v5
  with:
    context: .
    push: true
    tags: ${{ steps.meta.outputs.tags }}
    labels: ${{ steps.meta.outputs.labels }}
    cache-from: type=gha
    cache-to: type=gha,mode=max
```

## How to Use the Workflow

The daily use is short.

First, make normal commits:

```bash
git commit -m "fix(mermaid): fix node text clipping in flowchart diagrams"
git commit -m "feat(about): rewrite About page and homepage description"
git commit -m "docs(posts): update GitHub Actions release guide"
git commit -m "chore: add wrangler.toml for Cloudflare Workers static deployment"
```

When it is time to release, update `VERSION`:

```txt
1.0.2
```

Then commit and push:

```bash
git add VERSION
git commit -m "chore: release 1.0.2"
git push origin main
```

Open GitHub and check:

```text
Actions -> Release
```

When the workflow finishes, check:

```text
Releases -> v1.0.2
```

## Keeping package.json in Sync

If the project is a Node application, it is usually worth keeping `package.json` and `package-lock.json` aligned with `VERSION`.

Use:

```bash
npm version 1.0.2 --no-git-tag-version
```

Then commit all version files together:

```bash
git add VERSION package.json package-lock.json
git commit -m "chore: release 1.0.2"
```

The workflow still reads `VERSION`. Updating `package.json` is about consistency, not triggering the release.

## Common Mistakes

The most common mistake is reusing a version that already has a tag. If `v1.0.1` exists, setting `VERSION` to `1.0.1` will not publish another release.

The second mistake is writing vague commit messages for changes that should be visible in the release. This works:

```bash
git commit -m "update"
```

But it is omitted from the release notes because it is not `fix` or `feat`.

This is better for a real bug fix:

```bash
git commit -m "fix(search): keep modal results scrollable on mobile"
```

It produces a useful changelog entry:

```md
- search: keep modal results scrollable on mobile (commit_hash)
```

The third mistake is expecting normal pushes to publish releases. This workflow only releases when `VERSION` changes on `main`, by design.

## Branch Protection

Because releases are triggered from `main`, it is worth protecting the branch.

For a small personal project, a minimal rule is enough:

```text
Block force pushes
Restrict deletions
```

For a team project, add pull requests and required checks:

```text
Require a pull request before merging
Require status checks before merging
```

Only enable required checks after a real CI workflow exists. A release workflow is not a replacement for CI because it only runs when `VERSION` changes.

## Final Checklist

Before publishing a release:

1. Commit messages use `fix(...)`, `feat(...)`, or a clear maintenance prefix.
2. Article and documentation edits use `docs(posts): ...` so they stay out of Release Notes.
3. `VERSION` contains the new version.
4. `package.json` and `package-lock.json` match, if the project uses npm versioning.
5. The version has not been released before.
6. The release commit is pushed to `main`.

That is the whole system. The workflow is not clever; it is predictable. The `VERSION` file decides when a release happens, the git tags decide what changed, and the commit messages decide how the release notes read.

Conventional Commits — это лёгкая спецификация для сообщений коммитов. Основная идея: структурированный префикс сообщает людям и инструментам, какой тип изменений содержит коммит. Это позволяет автоматизировать changelog, Release Notes и семантическое версионирование.

## Формат

```
<тип>(<область>): <описание>

[необязательное тело]

[необязательные примечания]
```

### Минимальный пример

```
fix: исправить переполнение навигации на мобильных устройствах
```

### С областью

```
feat(auth): добавить вход через GitHub OAuth2
```

### Полный пример

```
feat(api): добавить пагинацию в эндпоинт /posts

Возвращает до 20 записей на страницу. Клиенты передают ?page=N
для получения следующих страниц.

Closes #142
Co-Authored-By: Alice <alice@example.com>
```

## Типы

Тип — единственная обязательная часть помимо описания. Ниже стандартные типы:

| Тип | Когда использовать | Раздел в Release Notes |
|---|---|---|
| `feat` | Новая функциональность или изменение поведения | **Features** |
| `fix` | Исправление ошибки | **Bug Fixes** |
| `docs` | Только документация | (обычно не включается) |
| `style` | Форматирование, пробелы — без изменения логики | (обычно не включается) |
| `refactor` | Рефакторинг — без исправлений и новых функций | (обычно не включается) |
| `perf` | Улучшение производительности | **Performance** |
| `test` | Добавление или исправление тестов | (обычно не включается) |
| `build` | Система сборки, зависимости | (обычно не включается) |
| `ci` | Конфигурация CI | (обычно не включается) |
| `chore` | Рутинные задачи обслуживания | (обычно не включается) |
| `revert` | Откат предыдущего коммита | **Reverts** |

:::tip
Спецификация требует только `feat` и `fix`. Остальные — общепринятые соглашения, которые понимают инструменты, но вы можете определить свои типы для внутреннего использования.
:::

## Область (Scope)

Область — необязательное существительное в скобках, описывающее часть кодовой базы, которую затрагивает изменение:

```
feat(search): добавить полнотекстовый поиск в блог
fix(toc): исправить якорные ссылки для кириллических заголовков
feat(api): добавить ограничение запросов
fix(deps): обновить next с 15.0.0 до 16.0.0
```

Хорошие области:
- Названия компонентов (`header`, `footer`, `sidebar`)
- Названия модулей (`auth`, `api`, `db`)
- Зоны (`config`, `deps`, `ci`)

Жёстких правил нет — придерживайтесь единого стиля в проекте.

## Ломающие изменения (Breaking Changes)

Ломающее изменение обозначается одним из двух способов:

**1. Восклицательный знак после типа/области:**

```
feat!: удалить эндпоинты /v1 API
fix(auth)!: токены теперь истекают через 1 час, а не 24
```

**2. Примечание с `BREAKING CHANGE:`:**

```
feat(api): переработать процесс аутентификации

BREAKING CHANGE: Формат заголовка Authorization изменён
с `Bearer <token>` на `Token <token>`. Клиенты должны обновиться.
```

Оба способа создают раздел **Breaking Changes** в changelog и запускают обновление **major** версии в инструментах семантического версионирования.

## Как это использует pipeline выпусков этого блога

Рабочий процесс GitHub Actions в этом репозитории читает темы коммитов с момента последнего тега и классифицирует их:

```bash
# коммит: "fix(footer): сделать хеш коммита кликабельной ссылкой"
# → появляется в Bug Fixes как:
#   - footer: сделать хеш коммита кликабельной ссылкой (4db55bb)

# коммит: "feat(search): добавить модальное окно полнотекстового поиска"
# → появляется в Features как:
#   - search: добавить модальное окно полнотекстового поиска (a1b2c3d)
```

Рабочий процесс убирает префикс `fix:` / `feat:` и форматирует область как метку, создавая такие Release Notes:

```markdown
## Bug Fixes

- footer: сделать хеш коммита кликабельной ссылкой (4db55bb)
- toc: slugify теперь поддерживает кириллицу (dd083ba)

## Features

- добавить GitHub Actions pipeline выпусков (bd1c006)
- search: добавить модальное окно поиска (a1b2c3d)
```

Коммиты без распознанного префикса попадают в **Other Changes** и не засоряют основные разделы.

## Практические правила

**Одно логическое изменение на коммит.** Не смешивайте исправление ошибки и новую функцию в одном коммите — тип не может быть одновременно `fix` и `feat`.

**Пишите описание в повелительном наклонении.** Говорите, что коммит *делает*, а не что он *сделал*:

```
# Хорошо
fix: обработать нулевого пользователя в middleware сессии
feat: добавить переключатель тёмной темы

# Плохо
исправил: нулевой пользователь не обрабатывался
добавлена тёмная тема
```

**Описание должно дополнять фразу «Этот коммит…»**

```
feat(rss): добавить поддержку JSONFeed 1.1
# → «Этот коммит добавит поддержку JSONFeed 1.1»
```

**Держите строку темы в пределах 72 символов.** Более длинные описания помещайте в тело коммита.

## Настройка Commitlint (опционально)

Для автоматической проверки формата при каждом коммите:

```bash
npm install --save-dev @commitlint/cli @commitlint/config-conventional husky
```

`commitlint.config.js`:

```javascript
export default {
  extends: ["@commitlint/config-conventional"],
};
```

`.husky/commit-msg`:

```bash
#!/bin/sh
npx commitlint --edit "$1"
```

После настройки каждое сообщение коммита будет проверяться перед сохранением. Несоответствующие сообщения отклоняются с понятной ошибкой.

## Краткий справочник

```
feat: новая функциональность
fix: исправление ошибки
feat(область): новая функция в конкретной части
fix(область): исправление в конкретной части
feat!: ломающая новая функция
fix!: ломающее исправление
docs: обновление документации
refactor: рефакторинг кода
perf: улучшение производительности
chore: рутинное обслуживание
```
